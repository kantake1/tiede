作業の正 (状態・議論) は [GitHub Issues](https://github.com/kantake1/tiede/issues)。このファイルは全体像の要約だけを持ち、詳細は各 Issue を見る。Issue を閉じたり優先度を変えたら、ここも更新する。

## 今の重点

1. **開発の土台**: 確認作業を自動化し、本番データを汚さない (#1, #3)

## 進める順番

**#5 (並行) → #3 → #1 → #4 → #2 → #7 → #10 → #8 → #6 → #9**

| 順 | Issue | 理由 |
|---|---|---|
| 並行 | #5 実機での確認 | オーナーがすぐ実施できる。見つかった不具合は最優先になるため、先に済ませて計画のぶれを防ぐ |
| 1 | #3 テスト用データの分離 | #1・#4 の前提。本番を汚さずにテストできる環境を先に作る |
| 2 | #1 テスト・プレビュー・公開の自動化 | 以降すべての確認コストを下げる。PR ごとのプレビュー URL で実機確認がしやすくなる |
| 3 | #4 Firestore への App Check の強制 | 判断材料 (検証済みリクエストの割合) は #3・#1 の間に貯まる。今日からコンソールで確認を始める |
| 4 | #2 レシートの個人品目 | 利用者への効果が最大。見本の確認に #1 のプレビュー URL を使う |
| 5 | #7 キャッシュ名の自動更新 | #1 の自動公開に組み込むと自然 (完了) |
| 6 | #10 読み取り精度の検証 | #2 の完成後、実際のレシートで試すついでに行う |
| 7 | #8 初回読み込みの軽量化 | #5 で遅さを感じるかを見て判断 (実測して対応済み) |
| 8 | #6 グループの完全な削除 | 安全な仕組みの設計が必要。テスト用の掃除は #3 で済む |
| 9 | #9 送金済みチェック | 実際に使ってから要否を判断 |
